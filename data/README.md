# `data/` — generated datasets

Three JSON files, each a flat array of rows:

| file | rows | generated by |
|---|---|---|
| `nba-players.json` | player-seasons | `tools/build-nba-data.mjs` |
| `nfl-players.json` | player-seasons | `tools/build-nfl-data.mjs` |
| `nfl-units.json` | unit-seasons | `tools/build-nfl-data.mjs` |

**Never hand-edit any of them.** Fix the generator, re-run it, commit the output.
See `tools/README.md`.

## Why JSON and not a JS module

They were ES modules exporting an array (`export const PLAYERS = [...]`), which
meant a browser had to parse 5.2MB of football as JAVASCRIPT before a single
name could be drafted. Measured on the NBA file alone — 2.3MB — importing the
module took 135ms against 29ms to `JSON.parse` the identical payload, a 4.7x
difference, and a phone's CPU multiplies that gap rather than closing it.

A JSON file is also cacheable on its own terms. The modules were reached
through `import()` from `js/sports/<id>/index.js`, so they shared the app's
cache lifetime; the datasets change when a season is added and the app changes
several times a week, and those are different clocks.

## Reading them

Nothing imports these files directly, in either environment:

- **Browser** — `js/sports/<id>/index.js` fetches on demand, when the sport is
  chosen. Basketball never pays for football.
- **Node** (tools, checks) — `import { loadDataset } from "../data/load.mjs"`.

`data/load.mjs` is the only reader. It exists so that "where does the data live
and what is it called" is answered once rather than in twenty-two scripts, which
is what made the format impossible to change before.
